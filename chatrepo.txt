The remaining burnout is not a milliseconds vs microseconds bug. It is a scheduling bottleneck.

The key trace is this: start_time is set once at initialization in initializer.c:74, every coder starts with last_compile_start = 0 in initializer.c:28, and the monitor checks burnout before a coder has compiled even once in stoppers.c:40 and monitor.c:18. That is fine if the first compile happens quickly. It fails because acquire_dongles still sends every coder through a single global queue gate in dongle_manager.c:69, backed by the FIFO and EDF waits in scheduler.c:74 and [src/scheduler.c](src/scheduler.c#L89]. So coders do not just contend for dongles, they wait their turn to even try.

The exact suspicious functions are:

dongle_manager.c:69 and scheduler.c:74: this is the main bug. FIFO and EDF are implemented as an exclusive turnstile, so only one coder can progress at a time. That kills concurrency and guarantees starvation under large N.
stoppers.c:40 and stoppers.c:66: check_burnout_timeout treats last_compile_start == 0 as elapsed time since start_time, which means coders still waiting for their first turn are already aging toward burnout.
initializer.c:28 and initializer.c:74: initialization is correct, but it makes the above timing policy visible immediately.
engine.c:39: last_compile_start is updated at compile start, not compile end. That is not the main failure here, but it means the compile duration itself is part of the burnout window.
scheduler.c:18: EDF gives every unstarted coder INT_MAX on the first pass, so it does not solve the first-cycle bottleneck.
monitor.c:18: it busy-spins and catches the failure immediately, but it is only exposing the problem.
utils.c:85: the cooldown placement bug was the old issue, but after the release-order change it is no longer the root cause of these large-test failures.
